# AuthSentry: SOC log detection lab

AuthSentry reads **Linux OpenSSH auth logs** and **Windows Security events (4624, 4625, 4740)**. It runs **YAML detection rules** for brute force, password spraying, a successful login after failures, and account-lockout bursts. Each alert becomes an **incident report** with a MITRE ATT&CK technique, evidence lines, triage steps and an escalation note.

It is a small, readable detection pipeline for learning SOC triage: **parse → normalise → detect → report**. It is not a SIEM and does not replace Wazuh, Splunk or Sentinel.

**Live demo:** https://authsentry.vercel.app. Paste a log or load a sample, then press Analyze.

## Detection rules (`authsentry/rules/default.yaml`)

| ID | Rule | Logic (default) | Severity | MITRE ATT&CK |
|---|---|---|---|---|
| AS-001 | Brute force against one account | ≥ 5 failed logins, same source IP + account, within 5 min | high | T1110.001 Password Guessing |
| AS-002 | Password spraying from one source | ≥ 4 different accounts failed from one IP within 10 min | high | T1110.003 Password Spraying |
| AS-003 | Successful login after repeated failures | a success from an IP that had ≥ 3 failures in the previous 10 min | critical | T1078 Valid Accounts |
| AS-004 | Account lockout burst | ≥ 3 lockouts (4740) on one host within 15 min | medium | T1110 Brute Force |

Rules are data, not code. You can change thresholds, windows, `group_by` fields (`src_ip`, `user`, `host`, `source`, `workstation`), severity, triage steps and the escalation policy without touching Python. A bad rule file fails fast with a clear error.

**Windowing:** a rule fires when the threshold is met inside one sliding window. The alert then stays open and absorbs later events that come within one window of the previous one. A 40-minute attack becomes **one** incident, not dozens.

## Inputs

- **Linux:** `/var/log/auth.log`, `/var/log/secure` or a journald export. Classic syslog timestamps (`Nov 23 09:00:01`, with `--year` because syslog has no year; a Dec → Jan rollover is handled) and RFC 3339 timestamps both work. `sshd` and the newer `sshd-session` process names both work. Only sshd's own `Failed …` / `Accepted …` lines are counted. PAM's duplicate `authentication failure` lines are ignored, so one attempt counts once.
- **Windows:** events 4624, 4625 and 4740 as a JSON array or JSON lines. Flat exports (`Get-WinEvent … | Select-Object …`, including PowerShell's `/Date(ms)/` timestamps) and nested EVTX-to-JSON exports (`System` / `EventData`, `Data[{Name, #text}]`) both work. Other event IDs are counted and skipped.

## Run it

```bash
pip install -r requirements.txt
python -m authsentry samples/linux_auth.log --year 2026            # Markdown incident report
python -m authsentry samples/windows_security.json --json          # JSON for other tools
python -m authsentry /var/log/auth.log --fail-on high -o report.md  # exit code 2 if any high/critical alert
python scripts/dev_server.py                                       # web demo on http://127.0.0.1:8000
```

API (the same handler runs on Vercel):

```bash
curl -s -X POST https://<deployment>/api/analyze -H 'Content-Type: application/json' \
  -d '{"log": "Nov 23 09:00:01 web01 sshd[1]: Failed password for root from 203.0.113.45 port 4 ssh2", "year": 2026}'
```

## Sample data

`samples/` is synthetic and generated by `scripts/make_samples.py`. It uses only documentation IPs (RFC 5737) and private ranges.

- `linux_auth.log`: root brute force from 203.0.113.45, a spray across 6 accounts from 198.51.100.23 that ends in a successful `deploy` login, plus benign activity that must **not** alert: a typo followed by a good login, and slow guessing below the threshold.
- `windows_security.json`: an RDP brute force on `Administrator` that then succeeds, and an internal spray from `WS-114` that locks out 3 accounts.

## Tests

```bash
pip install -r requirements-dev.txt && pytest -q
```

48 pytest tests cover the parsers (both timestamp styles, year rollover, IPv6, nested Windows JSON), rule thresholds and window edges, false-positive cases, rule-file validation, the Markdown/JSON reports, the API's input checks and the CLI. GitHub Actions runs them on Python 3.10 – 3.12.

## Security notes

- The web page renders every log value with `textContent`, so a hostile log line can't inject HTML. A strict Content-Security-Policy (`script-src 'self'`) is set in `vercel.json`.
- The API accepts JSON only, caps the body at 1 MB, validates every field, and keeps nothing: logs are analysed in memory and dropped.
- Don't paste production logs with real user data into a public demo. Use test or redacted logs.
